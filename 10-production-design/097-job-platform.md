# 097 系统设计：如何构建支持重试的异步任务平台？

> 难度：高级 · 分类：生产与系统设计

## 简短回答

平台需要持久任务记录、明确状态机、有界 worker、租约与超时、幂等执行和可恢复调度。任务“领取成功”与“业务完成”是不同事件；worker 崩溃后允许重新执行，核心副作用必须能够识别重复或拒绝旧执行者。

## 详细解析

### 最小完整状态模型

任务记录包含 task_id、业务幂等键、状态、计划时间、尝试次数、租约到期、执行世代与结果位置。状态可以是 pending、running、succeeded、retry_wait、failed、cancel_requested；具体名称不重要，重要的是每个转移都有前提和持久证据。

```text
pending → running → succeeded
             ├→ retry_wait → running
             └→ failed
running 的租约过期 → 按预算重新领取，生成更高执行世代
```

提交接口以业务键去重，在持久化完成后返回任务 ID。调度器按到期时间选取任务，领取时原子更新租约和世代，避免多个 worker 同时认为自己持有当前执行权。

### 租约过期不等于旧任务停止

worker A 暂停后租约过期，B 接管；A 恢复仍可能继续执行。更新任务结果时要带执行世代条件，防止旧结果覆盖新结果。若任务调用外部系统，结果表的世代检查还不足以阻止旧副作用，需要下游幂等键或资源端 fencing。

心跳延长租约只是降低误接管概率，不能提供强杀保证。任务取消同样是协作式的：标记 cancel_requested，通知当前 worker，在可中断点停止；已经提交的付款不能通过改状态假装撤销。

### 调度与资源隔离

不同任务类型可能分别受 CPU、内存、数据库或第三方配额限制，应有独立并发预算。大租户不能占满全局队列，可用分组配额和公平调度。优先级机制还要避免低优先级永久饥饿，定义最大等待或提升策略。

失败按可重试性分类，退避和次数预算持久化，避免重启后重置计数。长时间等待不要占着 worker 睡眠；计划时间到达后再进入可执行集合。结果和日志有保留期限，敏感任务载荷不应无限保存。

### 验证恢复而不只验证成功

在领取后、副作用后、结果提交前分别终止 worker，检查任务能恢复且业务不重复。模拟调度器重启、时钟偏差和数据库短暂故障，观察最老任务年龄、租约接管次数和重试比例。实例存活不代表任务平台在推进。

## 常见误区 / 面试追问

- **任务队列存在 broker 里就不用数据库状态吗？** 取决于查询、审计、计划和恢复需求，broker 交付状态未必等于业务状态。
- **能承诺任意任务恰好执行一次吗？** 通常不能，尤其是任意外部副作用；应承诺清楚的交付和幂等边界。
- **任务特别慢就把租期无限延长吗？** 会损害故障恢复，应保留心跳、上限与可接管协议。
